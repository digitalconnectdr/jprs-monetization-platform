# Fase 4 — CMS & Product Intelligence

Fuente: `docs/PROJECT_BLUEPRINT.md` §11 ("CMS & Product Intelligence — Productos, vendors, fuentes, precios, content workflow, freshness") y §5 (dominios `catalog`/`content`/`operations`). Iniciada 2026-08-08.

## Scope

- **Catalog completo**: `product_variants`, `product_features`, `product_prices`, `product_media` — el shell mínimo de Fase 2 (`vendors`/`products`) se completa con las tablas que el blueprint §5 exige, incluyendo `source`/`checked_at`/`confidence` en todo precio/feature (regla de datos, §5).
- **Historial, no sobrescritura**: `product_prices` y `product_features` son **append-only** — cada cambio es una fila nueva, nunca un `UPDATE`. Se aplica como garantía técnica (RLS sin policy de `update` para nadie, ni siquiera admin) en vez de solo una convención documental.
- **Content workflow**: `content_items` (unidad publicable — Best X, VS, Review, etc.), `content_versions` (versionado real, con `review_state`), `content_blocks` (contenido estructurado por versión), `content_product_links` (qué productos menciona/compara cada pieza), `content_sources` (fuentes citadas por versión).
- **Enforcement técnico de ADR-005** (no auto-publicación sin revisión humana): un `content_item` solo puede pasar a `status='published'` si apunta a una `content_version` con `review_state='approved'` — verificado por trigger, no solo por convención de UI (que todavía no existe).
- **Freshness**: `freshness_checks` (dominio `operations`) — registro de qué entidades (`product_price`, `product_feature`, `content_item`) necesitan revisión y cuándo. Sin UI ni cron todavía (Supabase Cron/Edge Functions para disparar los checks automáticamente es Fase 9, "AI Operations & Freshness" — aquí solo se modela el dato).
- **Bulk import validation**: función SQL `public.import_product_prices(rows jsonb)` que valida cada fila (producto existe, `amount >= 0`, `currency` de 3 letras, `price_type` válido, `source` no vacío) y rechaza las inválidas fila por fila con motivo, sin abortar el lote completo.
- Tests de acceso positivo/negativo contra el proyecto Supabase real (sin preview DB — ADR-012), extendiendo el patrón de `supabase/tests/rls_access.test.mjs`.

## Explícitamente fuera de scope (no adelantar)

- **UI de administración/CMS** (formularios para crear/editar productos, precios, contenido). Motivo concreto, no genérico: `apps/web` no tiene ningún cliente de Supabase instalado todavía (`@supabase/supabase-js`/`@supabase/ssr`) — no hay sesión de servidor, no hay página de login, no hay forma de que un usuario autenticado llegue a una ruta protegida. Construir eso a medias en esta fase (sin login real) sería peor que no construirlo. Backlog 204 (Admin/User route guards) se re-difiere una vez más — ver nuevo ítem de backlog para el wiring de auth que es su prerrequisito real.
- **Cron/Edge Functions que disparen freshness checks automáticamente** — eso es Fase 9 (AI Operations & Freshness). Aquí `freshness_checks` es solo el dato, no el job.
- **Contenido editorial real** (comparativas, reviews reales de producto) — eso es Fase 6A/6B/6C (seed editorial por vertical). Fase 4 deja el schema listo para recibirlo, no lo llena.
- **Endpoint HTTP/API route para bulk import** — la función SQL es el mecanismo de validación; exponerla vía una ruta de Next.js requiere la misma auth que la UI de admin (ver primer punto), así que también se difiere.

## Entregables

- Migraciones: `product_variants`, `product_features`, `product_prices`, `product_media`, `content_items`, `content_versions`, `content_blocks`, `content_product_links`, `content_sources`, `freshness_checks`, función `import_product_prices`.
- RLS + `GRANT` explícito en cada tabla nueva (patrón ya establecido, incluye `service_role` desde el día uno para no repetir el hallazgo F-07 de Fase 2).
- Tests de acceso positivo/negativo + validación de import, corridos contra el proyecto real.
- `docs/DATA_DICTIONARY.md` actualizado con los 3 dominios nuevos.

## Auditoría de cierre

Toca schema/RLS — **A3 (Security & RLS) obligatorio por ADR-011**, sin excepción, igual que Fase 2.

## Criterios de aceptación (blueprint + decisiones de esta fase)

- [x] CRUD de catalog (variants/features/prices/media) funciona con autorización correcta (editor/admin del site correspondiente).
- [x] Todo precio/feature tiene `source` + `checked_at` + `confidence` — no puede insertarse sin ellos.
- [x] Ningún precio/feature histórico puede sobrescribirse (`UPDATE` bloqueado por RLS para todos los roles, incluido `service_role` tras corrección F-05).
- [x] Content workflow: un `content_item` no puede quedar `published` sin una `content_version` propia con `review_state='approved'` — corregido tras F-01 (Critical), la versión inicial no validaba pertenencia al mismo item.
- [x] Bulk import rechaza filas inválidas sin abortar las válidas del mismo lote.
- [x] Todas las tablas nuevas tienen RLS explícito, verificado con tests reales (29/29, incluye los 4 casos negativos de la auditoría).
