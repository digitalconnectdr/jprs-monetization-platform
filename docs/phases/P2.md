# Fase 2 — Data Core, Auth & RBAC

Fuente: `docs/PROJECT_BLUEPRINT.md` (Modelo de datos y RBAC, Plan maestro por fases). Iniciada 2026-08-08.

## Scope

- Schema base para los dominios `identity`, `properties` y un shell mínimo de `catalog` (el catálogo completo con variants/features/prices/media es Fase 4).
- Supabase Auth wired con `profiles` (trigger `on auth.users insert`).
- RBAC con RLS: los 6 roles del blueprint (Super Admin, Admin, Editor, Analyst, User, Vendor), con scope por `site_id` donde aplica.
- Migrations idempotentes en `supabase/migrations/`, seed controlado en `supabase/seed.sql`.
- Tests de acceso positivo/negativo contra el proyecto Supabase real (sin preview DB — ver ADR-012).

## Explícitamente fuera de scope (no adelantar)

- CRUD completo de productos/vendors, versión de contenido, freshness — eso es Fase 4.
- UI de admin o de cuenta de usuario — eso es Fase 3 (Design System & Public Shell) en adelante.
- Affiliate/ads/monetization tables — Fase 5.
- Analytics/events tables — Fase 7 (aunque `operations.audit_findings`/`backlog_items` podrían anticiparse si hace falta trazabilidad real del propio proceso, se evalúa aparte, no por defecto).

## Entregables (según blueprint)

- Migrations
- RLS policies
- Auth flows (mínimo: signup/login vía Supabase Auth, creación automática de `profiles`)
- DB tests (positivo/negativo)
- `docs/DATA_DICTIONARY.md`

## Auditoría de cierre

A2 (Architecture) / **A3 (Security & RLS) obligatorio** / A4 (QA). Por ADR-011, todo PR de esta fase que toque schema/RLS/auth lleva auditoría de agente independiente adjunta antes de mergear — sin excepción, es la zona de mayor riesgo del proyecto.

## Criterios de aceptación (blueprint)

- [x] Usuario normal no puede leer/escribir datos admin. — verificado empíricamente, ver `docs/phases/P2_REPORT.md`.
- [x] Admin scope funciona por property (`site_id`). — verificado empíricamente.
- [x] Todas las tablas sensibles tienen RLS explícito. — 10/10 tablas.

**Cerrada 2026-08-08.** Reporte de cierre: `docs/phases/P2_REPORT.md`. Auditorías: `docs/audits/P2_AUDIT.md`.

## Decisión de infraestructura relevante

**ADR-012**: sin Database Branching (requiere plan Pro), las migraciones se revisan como código SQL en PR y se aplican directo al único proyecto Supabase después de mergear a `main`. Riesgo aceptado: sin datos reales de usuarios todavía.
