# Fase 7 — Admin Analytics & ROE v1

Fuente: `docs/PROJECT_BLUEPRINT.md` §7 (ROE), §8 (Analytics/KPIs), `docs/KPI_TREE.md` (event taxonomy, fórmulas, dashboard admin, gates económicos). Iniciada 2026-08-11, tras cerrar las 3 verticales del MVP (Fase 6A/6B/6C).

## Bloqueo real descubierto al iniciar esta fase (no es scope creep, es un prerrequisito)

El blueprint (§7.5, Dashboard administrativo) asume un panel accesible solo a roles internos (`admin`/`analyst`/`super_admin`). **`apps/web` no tiene ningún wiring de autenticación/sesión** — backlog 409, TODO desde Fase 4, re-diferido en Fase 3/4/5/6A/6B/6C sin bloquear ninguna de esas fases porque ninguna necesitaba una UI protegida. Fase 7 sí la necesita: un dashboard ejecutivo/afiliados/productos servido sin gate de sesión sería, en el mejor caso, una promesa falsa de seguridad, y en el peor, una fuga de datos de negocio (comisiones, revenue por vertical) a cualquier visitante anónimo.

**Decisión de scope**: esta sesión NO construye la UI del dashboard (701-704, 706 del blueprint). Construye la base de datos que el dashboard necesitará (event ingestion real, funcionando, con datos reales aunque escasos) y una primera versión honesta de ROE v1. La UI del dashboard queda como el primer ítem de la siguiente fase de UI de administración, condicionado a resolver 409 primero — no tiene sentido diseñar pantallas para datos que ni siquiera se están capturando todavía.

## Segundo bloqueo real: ROE v1 tal como lo define el blueprint requiere tráfico real que no existe

La fórmula de §7 (`Expected Revenue per Session = Ad EV + Affiliate EV + Lead EV + Sponsor EV`) depende de `P(click)`, `P(conversion | click)` y RPM reales — señales que solo existen con tráfico real. El proyecto está pre-lanzamiento (Fase 11, MVP Launch, no ha empezado); no hay una sola sesión de visitante real registrada todavía. Calcular esa fórmula hoy significaría inventar probabilidades — exactamente el tipo de dato fabricado que `CONTENT_POLICY.md`/`CLAUDE.md` prohíben, aplicado ahora a analytics en vez de a contenido editorial.

**Decisión de scope**: `roe_scores` (Fase 5) se puebla con un **score de completitud/frescura estructural** (¿tiene precio?, ¿tiene features con fuente real?, ¿qué tan reciente es `checked_at`?) explícitamente etiquetado como `methodology='structural_readiness_v1'`, no como el ROE real del blueprint. Es una señal honesta y útil hoy (qué tan "listo para monetizar bien" está un producto), pero no simula tráfico que no existe. La fórmula completa de ROE se implementa cuando exista tráfico real que medir (después de Fase 11).

## Scope real de esta sesión

- **Event schema real**: tabla `analytics_events` (event_type + event_id idempotente + site_id + payload), cubre los 9 tipos de evento de `KPI_TREE.md` §3. RLS: `anon` puede insertar (telemetría del sitio público) pero nunca leer; lectura solo `analyst`/`admin`/`super_admin` vía roles existentes de Fase 2.
- **Función de ingesta idempotente**: `record_analytics_event(...)`, mismo patrón que `record_affiliate_click`/`import_revenue_events` (Fase 5) — `ON CONFLICT (event_id) DO NOTHING`.
- **Un evento real, cableado de punta a punta como prueba**: `page_view` emitido desde el shell público (`apps/web`) en cada navegación — verificado con eventos reales llegando a la tabla, no solo la función probada de forma aislada.
- **ROE v1 estructural**: función que calcula `roe_scores.quality_score` (completitud de datos: precio presente, ≥N features con fuente, frescura de `checked_at`) para los productos ya sembrados en las 3 verticales — sin tocar `monetization_score` (eso sí requiere señales de afiliados que no existen — backlog 608/618/628).
- **Tests de acceso** (positivo/negativo) para RLS de `analytics_events` y para la función de ingesta.

## Explícitamente fuera de scope

- **UI del dashboard administrativo** (los 8 módulos de `KPI_TREE.md` §5) — bloqueado por backlog 409 (auth/sesión). Se construye en cuanto 409 se resuelva.
- **`product_impression`, `affiliate_click`, `comparison_add`, `save_product`, `lead_start`/`submit`, `conversion`, `ad_revenue_daily`, `newsletter_signup` cableados end-to-end** — el schema los soporta todos desde el día uno (misma tabla genérica), pero solo `page_view` se cablea realmente esta sesión como prueba del pipeline. Cablear el resto requiere UI que en algunos casos no existe todavía (ej. `affiliate_click` real necesita `affiliate_links` conectados — 608/618/628, todos TODO).
- **ROE `monetization_score` y la fórmula completa del blueprint** — requiere tráfico real; ver "Segundo bloqueo" arriba.
- **Reconciliación de eventos** (`KPI_TREE.md` criterio "≥98% eventos críticos") — no aplica todavía sin volumen real que reconciliar.
